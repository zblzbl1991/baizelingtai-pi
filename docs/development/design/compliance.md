# 合规审查：需求与设计讨论

状态：产品决定已逐项确认，用户已授权先补齐规格和实现票再开发；实现规格草案待核对，功能未实现。本文不表示功能已部署或已发布。

本文记录已确认的要求、职责分工和后续规格需细化的事项。业务术语见 [业务术语](../../../GLOSSARY.md)。不保存真实工程项目资料、个人信息或运行实例资料。

## 整体方案

第一版面向一名审查人员，通过现有聊天完成单个工程项目的资料整理、四组检查、人工复核及报告交付。

| 部分 | 职责 |
|---|---|
| 内置能力开关 | 在统一设置入口启用或禁用合规审查，控制相关入口及执行资格 |
| 专用合规主智能体 | 理解要求、安排步骤、调用工具、解释检查结果 |
| 四个 Skill | 分别规定资料整理、合规检查、问题复核和报告生成的操作步骤 |
| 随包 Pi 工具扩展 | 向已验证归属的专用智能体提供受控业务操作 |
| 合规审查模块 | 管理工程项目档案、资料快照、检查批次、规则执行、复核回执及报告 |
| 版本化规则包 | 保存适用条件、判断口径和例外，检查批次绑定实际使用版本 |
| 资料识别模型 | 从需要识别的页面中提取带出处的字段，保留日期精度及冲突 |
| 审查确认卡 | 由用户提交字段修正或最终结论，提交前核对当前结果是否变化 |
| 成果中心 | 保存按需交付并明确入库的 HTML 报告与 Excel 检查清单 |

日常流程：选择或建立工程项目档案 → 导入或选择资料 → 确认资料归属与检查范围 → 提取事实并执行规则 → 查看证据、修正与重算 → 用户确认 → 按需导出报告。

## 已确认的要求

1. 第一版供一名审查人员独立使用，由该人员导入资料、执行检查、核对问题并导出报告。多人共同处理同批资料的协作方式后续讨论。
2. 第一版验证单个工程项目从资料导入到报告生成的完整流程。先执行少量明确规则，支持查看证据、修正错误并重新检查。外部系统连接和批量工程项目检查后续增加。
3. 系统输出审查建议，由审查人员确认最终结论。明确区分系统发现与人工确认，保留原始判断及人工修正。
4. 第一版的验证重点是检查结果可追溯到原文，修正错误后可以得到正确的新结果。
5. 第一版通过现有聊天完成操作，提供可查看的检查明细和报告文件；专用管理页面后续增加。检查结果与修改记录须以结构化形式保留。
6. 第一版支持 PDF、图片和台账表格，补充扫描件识别。OFD、CEB、ZIP 和 RAR 后续支持；遇到这些格式时明确提示转换要求。台账表格的具体格式及识别实现待确认。
7. 首批规则包含四组：资料缺失与项目归属、可研评审与批复文号、合同签订期限、可研报告与评审时序。
8. 合同期限首批按“中标通知书下达后 30 日内签订”检查；可研时序按“可研报告日期早于评审日期”检查。日期计算及精度处理见下列已确认口径，字段取值来源等细节仍待细化。
9. 金额与分包规则待业务口径明确后加入。
10. 资料同时支持聊天上传和用户明确指定的已授权目录。系统只处理用户选定范围，并列出实际纳入检查的文件。
11. 合规审查模块保存工程项目档案、资料快照、检查批次和修改记录，报告对应指定批次。相同工程项目可以跨聊天继续审查，并追溯旧报告当时使用的资料。数据归属见 [ADR-0002](../../adr/0002-compliance-record-authority.md)。
12. 日期、项目归属等基础字段识别错误时，修正字段并重新计算受影响规则；保留原识别值、修正理由及前后检查结果。
13. 第一版使用一个专用合规主智能体，负责理解要求、调用工具和解释结果。普通资料提取与规则计算由工具完成，存在分歧的结果交人工复核；专家智能体后续根据实际案例按需增加。
14. 设置资料整理、合规检查、问题复核、报告生成四个 Skill。Skill 规定操作步骤与工具用法，规则包保存期限、适用条件和例外；每次检查记录所用规则版本。
15. 合规审查随白泽灵台内置，由用户选择启用或禁用，统一开关涉及的功能。须显式启用后才能使用，初期业务模块与 Pi 能力包随应用统一更新。交付方式见 [ADR-0003](../../adr/0003-compliance-optional-builtin.md)。
16. 能力开关覆盖相关功能入口、工具与 Skill；已有会话中如何投影和刷新实际可用资源仍待细化，服务端须核对功能是否启用。
17. 第一版在设置中提供当前白泽灵台实例的统一开关，作用于全部工作目录。初始关闭，启用只开放功能，不自动执行检查。
18. 有检查正在执行时请求禁用，停止接收新任务，当前步骤实际结束后暂停检查并保存进度；完全停止前显示停用中，完成后显示已禁用。重新启用后由用户选择是否继续检查。
19. 禁用保留工程项目档案、资料、检查结果和修正记录。已保存到成果中心的报告继续可查看，重新启用后可访问原档案。数据清理作为单独操作。
20. 在同一内置能力设置入口分别提供人员调配和合规审查开关，各自独立启停，两项能力分别保存业务数据并执行各自规则。
21. 合规审查首次启用提供引导，创建或关联专用智能体、配置四个 Skill 与工具、核对模型及扫描件识别能力；再次启用沿用已有配置和数据，核对配置是否可用，不重复创建智能体。
22. 合规工具与四个 Skill 默认仅向专用合规智能体开放，普通聊天可打开报告，并提供进入专用合规智能体的入口。
23. 整理资料时提取项目名称、编号、单位、年度和期次等身份信息，由用户确认工程项目档案。项目名称用于辅助判断；缺失信息保留为未知，归属冲突或不明确的文件单列待确认，经确认后再纳入检查。
24. 根据工程项目类型和当前阶段确定适用规则及必需资料。尚未适用的规则标为不适用；已适用但缺资料时记录资料缺失，依赖该资料的内容检查标为证据不足。
25. 每条规则分别记录检查结论和人工复核状态。检查结论采用通过、发现问题、证据不足、不适用；人工复核状态另行记录，工具执行失败单独报告，未完成检查不能视为通过。
26. 合同期限按自然日计算，中标通知书日期计为第 0 天。同日和第 30 天签订均满足期限，第 31 天及以后记录超期候选问题，早于通知书日期签订记录时序候选问题，两类原因分别说明。
27. 可研报告与评审时序按早于严格比较。同日不满足该规则，附原文证据列为候选问题，供人工复核。
28. 保留日期原始精度。仅到月份的日期按当月可能日期范围判断，能够确定结论时给出结论，不能确定时标为证据不足。日期缺失或来源冲突时列为待核对，不补造具体日期。
29. 文号检查以发文首页上方存在可识别的完整文号为通过条件。页面清晰但文号缺失时记录候选问题，模糊无法识别时标为证据不足，结果明确说明文号检查情况并保留原文位置。
30. 字段修正和最终结论确认通过聊天确认卡提交。卡片明确显示工程项目、检查批次、原值与新值或待确认结论，用户点击后保存操作回执。资料或结果已变化时，旧卡片须重新核对。
31. 第一版按需导出 HTML 详细报告和 Excel 检查清单。文件标明检查批次、规则版本、证据及复核状态，列出问题、证据不足、不适用和执行失败项，保留未完成检查的说明。
32. 分别配置主智能体模型和资料识别模型，支持两种任务的同一模型可同时使用。可复制文字先本地提取，扫描页交给支持图像输入的已配置资料识别模型。缺少扫描件识别能力时仍可检查文本资料，扫描项明确显示无法判断及原因，等待配置或人工补充。
33. 常规资料先识别一次，存在歧义时按需核验，为每批检查设置处理量和模型调用预算。达到预算后停止追加处理并保存进度，由用户选择缩小范围或继续。可估算时显示预计用量与费用，不能估算时明确标为未知。
34. 中断或故障后保留已完成资料处理与检查结果，由用户选择继续未完成项。网页断开不重复提交；服务重启后列出已完成项和待核对项，模型请求结果不确定时先核对可取得的操作状态，不自动重发，无法确认的请求保持待核对。
35. 普通聊天不新增本能力的提示说明、工具定义和 Skill 索引。只在能力已启用且专用智能体归属有效时加载，并核对实际模型请求；旧会话中的用户消息和工具历史继续保留。
36. 升级保留用户对专用智能体名称和行为说明的修改。四个内置 Skill 与规则包随应用统一管理，个人扩展单独保存。旧检查批次保持当时规则版本，采用新规则重新检查时建立新批次。
37. 验收先使用合成资料验证四组规则、日期边界、原文证据定位、过期确认卡与重复提交、禁用恢复及普通聊天加载范围，再用一套脱敏真实项目资料核对识别效果、处理耗时和模型费用；两类结果分别记录，保留误识别和证据不足项。

## 已核对的现有能力

- [办公附件](../../COMPOSER_TOOLS.md) 支持 DOCX、XLSX、PPTX 和 PDF 上传与按范围读取；当前 PDF 只提取可复制文字，不自动 OCR，也不接收普通压缩包。
- [助手档案](../../AGENT_PROFILES.md) 支持协作说明和技能设置；档案不构成用户权限隔离。
- [扩展与原生设置](../../NATIVE_SETTINGS.md) 管理 Pi 包、技能和 MCP 等资源；完整业务页面与服务接口需要在应用源码中接入。
- 当前原生资源停用控制发现与加载，不能据此认定已有会话中的指令已清除或业务功能已立即禁用。合规审查功能开关还需要宿主执行检查及界面状态配合。
- [成果中心](../../ARTIFACTS.md) 与 [文件交付](../../FILE_VIEWER.md) 可用于交付报告文件。

以上为源码能力依据，不表示当前运行实例已核验。

## 功能规格与实现设计需细化的内容

- 工程项目档案与资料的字段、台账表格的具体格式、必需资料清单、阶段适用表和字段取值位置。
- 数据存储结构、快照及规则版本保存、受控工具接口、修订校验、回执与并发提交处理。
- Pi 能力包登记方式、资源发现及工具注册前的归属过滤、已有会话的资源更新与加载确认。
- 主智能体与资料识别模型的用途接入、能力检查、预算默认值、初始化部分失败及模型不可用的具体状态。
- 用户自定义内容与受管资源的更新机制、确认卡交互、证据预览、HTML 与 Excel 报告模板。
- 根据脱敏样本确定识别质量、处理时间与费用的验收门槛，按开发流程安排专项、必要集成及独立身份的桌面和手机检查。

以上是后续规格与实现设计的工作项，不改变已确认的产品范围。技术方案及样本验证尚未完成，不将讨论决定视为已实现或已验收能力。

## 人员调配设计参考

参考 [人员调配设计讨论](staffing.md) 中已确认的内置可选能力、首次启用引导、再次启用复用配置与数据、停用保留数据。该文件同样标注功能未实现，不能视为可直接调用的现成功能。

已确认共用内置能力设置入口、各自独立开关，并采用首次启用引导及再次启用复用配置的方式。两项能力分别管理业务数据和检查约束。人员调配设计尚未规定运行中任务的停用流程，不能将其视为已经具有合规审查的停用中与步骤暂停语义。两项能力的 Skill 数量也按各自业务流程确定。

人员调配本地决策票另外提出了普通聊天避免新增业务 Skill 索引、工具定义及提示说明的验收目标。合规审查已确认采用该目标，但仍需实现和验证，不能视为已有上下文隔离能力。本地票属于另一项规划，不在本讨论中领取或修改。

## 本地决策跟踪

后续 wayfinder 规划使用 `.scratch/compliance/map.md` 作为地图，子票位于 `.scratch/compliance/issues/`。地图跟踪剩余规格前决定的依赖和进度，本文保留创建地图前已确认的产品要求。本地跟踪文件不纳入发行文档；创建地图这一轮只建图，不领取或解决子票。

用户随后调用 implement-spec，并明确选择“合规审查：先补齐规格和实现票，再开发”。实现规格草案位于 `.scratch/compliance-build/spec.md`，六张实现票草案位于其 `issues/` 目录。它们与原规划票分开，当前等待核对任务拆分与测试入口，不把未解决的规划票记为实施完成。
