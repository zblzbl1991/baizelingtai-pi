# 白泽灵台开发流程

## 从需求到交付

1. 用 [模块导航](MODULES.md) 找到职责所有者、现有契约和相关测试。确认源码分支、未提交改动，以及运行实例是否使用独立代码快照。
2. 写清改变的行为和影响范围。优先修改职责所有者；新增任务类型同时考虑运行、超时、停止、回收和维护空闲状态。
3. 开发时用有代表性的相关测试获得快速反馈。对协议、并发、身份、持久化和迁移增加行为测试；简单文案或低影响展示调整不必建立只重复实现的测试。
4. 按下表为本批选择验证级别和检查范围，同步该变化对应的文档。源码提交、本机启用、公开发布分别记录；不能因要提交或本机切换就自动升级为公开发布验收。跨平台或外部服务的验证范围如实记录。
5. 提交前检查 diff 和跟踪清单。需要部署时先完成候选、基线比对和备份准备；已有授权覆盖的工作继续执行。公开发布与本机部署是不同操作。

## 验证矩阵

按**实际影响范围**而非文件数、目录或“要部署了”分级。先写出改动行为、调用者/消费者、共享状态及失败边界，从 [模块导航](MODULES.md) 选测试；范围不明、基线不可信或出现跨模块回归时升到共享基础能力级。以下要求同时用于源码交付与本机部署准备；公开发布另有准确包门槛。

| 级别 | 适用边界 | 必须完成的验证 |
|---|---|---|
| 局部功能本机部署 | 功能内部逻辑、独立页面/样式；不改变共享契约、权限、生命周期、通用持久化、依赖或安装链 | 受影响 Node 专项及消费者/前后端必要集成；应用代码改动跑 `npm run check`；UI 跑相关 Chromium 桌面/手机脚本和相邻入口/共享外壳冒烟；文档变化跑 `npm run check:docs`。**不默认要求全量 Node、全量浏览器或三平台发行演练** |
| 共享基础能力部署 | RPC/worker/会话与并发、鉴权/文件身份、公共存储/迁移、网络/依赖/原生组件、安装/维护/源码发现；共享 UI 框架及跨模块装配 | 共享后端、依赖、安装等跑全量 `npm test`、`npm run check`、相关浏览器与集成；共享 UI（工作台、导航、输入区、正文渲染、设置框架、全局样式/加载链）跑全量 `npm run test:browser`、相关 Node 与语法。两侧都影响则两套全量都跑；无法证明只影响一侧时同样跑两套。文档、打包、平台与恢复专项按下表叠加 |
| 公开发布 | 明确准备公开发布的正式版本、对外下载归档及宣称支持的平台 | 全量 Node、语法、文档、全量自动浏览器及相关手动专项；按 [发布流程](RELEASING.md) 对**最终准确包**独立锁定安装、生产依赖审计、目标平台、安装/旧包升级/原路径恢复完整验收。不得用本机专项或源码结果替代 |

仅改文档/规则且未改变可执行文件或发行清单时，核对事实、规则一致性、`npm run check:docs` 和 diff 即可；不触发应用全量、浏览器、安装或部署。规则文本改变了验证/部署要求时还须人工核对相关自动化是否兼容，不能把文字约定宣称为已实现的自动检查。

| 附加影响 | 必须叠加的检查（不是每批都跑） |
|---|---|
| UI 与连接状态 | pageerror、实际子项宽度、抽屉、附件、草稿与工具状态；涉及线程/连接时覆盖切换、迟到事件和重连。修改共享文件中的孤立功能分支，只有证明共享行为未变并覆盖消费者后才可按局部级 |
| 跨工具/HTTP/WS/持久化链 | 用独立身份、真实装配的服务或受管 RPC 加合成供应商完成受影响端到端；静态 mock 或“全量已过”不能替代。写入需覆盖失败/不确定、修订冲突及不重放 |
| 公开清单、文件位置、发行链接、源码发现、打包、安装、路径兼容或维护 | 文档、`npm run pack:trial`、相应安装/更新/恢复与故障演练；迁移另须原生语义与字节校验 |
| 依赖、认证或网络边界 | `npm audit --omit=dev`、实际依赖解析及对应故障测试；依赖升级按 [依赖与上游适配](DEPENDENCIES.md) |
| 原生组件 | 源码/binary/manifest 一致性、目标平台编译和实机验证；不能用浏览器模拟替代 |

全量并未取消：共享能力改动、公开发布和累计集成检查仍执行。持续局部迭代时至少每周安排一次累计差异集成批次（全量 Node + 自动浏览器），记录最近基线和待验累计差异；到期未完成则在下一次本机部署前补齐，无迭代不要求空跑。已有符合条件的全量结果可作为该基线，不为“周检”再跑一次。这样避免独立脚本长期失效，又不把全量串在每次切换看效果之前。

测试必须有独立身份和合成服务，不在维护中的真实会话发送测试消息。测试通过不代表真实模型、媒体供应商、Safari 或其他系统已验收。

## 日常打包与验证复用

用户要求打包、重打包或升级版本并构建时，默认只构建本地候选并交付产物。使用 `pack:release`、生成新版本号或新归档 SHA256 本身不触发公开发布验收；明确要求验证、部署或准备公开发布时，再进入对应流程。

1. 核对工作区与本批变化，按下节引用已有验证的范围、证据和未覆盖项。仅修改版本元数据时，核对应用与 lockfile 根版本，以及需要重建的原生可执行文件版本、源码/binary/manifest 配对；不因此重跑应用回归。没有可复用证据的检查如实记为未验证，不为完成普通打包自动补齐全套。
2. 执行正常构建，保留打包器内置的私有数据排除、中性配置、原生一致性、固定资产哈希、依赖完整性和禁止覆盖同名包等保护。核对本次输出的版本、大小、SHA256，以及适用的校验和与更新清单；优先使用构建器生成的记录，同一产物只核对一次。
3. 源码、依赖、原生组件或构建链有实际变化时，按验证矩阵与复用规则补齐受影响检查及必要集成；本批已完成的检查直接引用。仅文档或版本元数据变化，以及新包名、新目录、新哈希，均不自动追加全量 Node、语法、浏览器/托盘、原生 Shell、解包验收或第二轮逐文件扫描。路径兼容相关检查由实际安装或路径行为变化触发。
4. 已知失败、超时或不确定结果保留原日志和限制。同一输入、同一失败不反复执行，也不通过预热、换临时目录、追加整批测试或文件扫描追求全绿；相关输入发生变化或用户要求诊断时，再做定向复验。构建器自身失败时停止并报告构建失败，不能绕过内置门槛。
5. 构建成功、产物版本与哈希记录齐备即完成普通打包，交付文件并简述复用证据与已知限制；无需继续做安装、部署或公开发布。构建成功只表示产物已生成，未完成的运行验收保持未验证状态。

Windows 便携构建使用显式公钥，只生成准确 ZIP、SHA256 与未签草稿；正式更新清单和离线包需维护者显式签名、验签组装，命令见[签名工具](UPDATE_SIGNING.md)。根 THIRD_PARTY_NOTICES.md 为仓库汇总说明，不随发行包提供；依赖原始许可证和 PORTABLE_NOTICES.txt 保留。

本节约束 Agent 选择验证范围，不表示构建脚本自动判断证据有效性。实际安装/部署仍执行现场门槛，明确准备公开发布仍执行最终准确包完整验收；这些操作按下节和 [发布流程](RELEASING.md) 处理。

## 验证结果复用与失效

复用的是**某一项检查的证据**，不是给候选整体贴“全量通过”。开发、冻结候选、本机启用前按以下规则核对一次，可只补差额：

1. 保存提交及脏工作区/精确文件清单哈希、检查命令与选择器、测试/fixture/运行器和生成 bundle 哈希、锁文件及实际依赖解析、OS/架构、Node/npm/Pi/原生组件、浏览器/Playwright 版本，以及影响该检查的配置、locale/时区和环境差异。只记录非秘密值或安全的证明引用；不保存凭据环境。记录时间、退出码、范围、日志位置/哈希、未覆盖项与原失败。
2. 同一源码、依赖和环境且上述输入未变，已通过的检查可复用；仅提交号、候选 ID、目录名改变不强制全套重跑，但须核对内容及路径/安装相关假设。只有锁文件相同不足以证明新安装依赖相同，候选仍核对实际解析、原生组件和启动。
3. 输入有变化时，列出差异和影响闭包，重跑受影响检查及必要集成。能证明与某检查无关的文档或其他层测试修改，不废弃该项证据；不能证明则补跑更大范围。应用/测试/fixture/运行器、生成资源、依赖、环境或配置变化均可能使结果失效，不能用“改动很小”代替证明。
4. 本机候选换目录/安装后，保留归档及逐文件核验、独立锁定安装、实际依赖核对、启动/能力探针和受影响集成；可复用已满足条件的源码 Node/浏览器结果，**不重复机械执行整套**。静态同步验证的是“当前运行版 + 本批文件”的组合，不能拿混有未部署后端的源码结果替代。公开发布仍需最终准确包的完整独立验收。
5. 失败、超时、截断日志或未知退出状态不是通过。查明原因后先复验失败及受影响项，保留初次失败和修正证据；环境变化影响范围不明时扩验。不要反复重跑到绿、删断言、放宽超时或把无法解释的偶发失败记为全量通过。
6. 审计依赖外部漏洞库，不能永久缓存：本机未改依赖/认证/网络且无新安全通告时，可复用 24 小时内同锁与同 registry 的成功 audit；否则刷新。公开发布必须刷新审计。

批次记录至少有：级别/判定理由、源码与运行差异、检查清单（`本次通过 / 复用 / 不适用 / 阻塞`）、每项证据与复用理由、累计全量基线、遗留风险。耗时分别记录测试、安装/打包、等待空闲、备份和切换，不能把会话总时长当作测试耗时。

**不可复用的部署现场门槛**：重新核对授权、active/previous、运行版修复、源码/候选/服务/配置绑定、当前队列与全局空闲；保留本次备份和完整性检查、只提交一次的票据/执行记录、启动与 HTTP 字节/能力核验。测试复用不授权跳过这些检查，不允许复用旧票据或不确定执行。

## Node 测试入口与计时

统一通过 `npm test` 运行，定向与全量执行使用相同的供应商环境凭据过滤和测试 bundle 配置。用例自身仍须创建独立身份与数据目录；运行器不把任意用例变成安全沙箱。

```bash
npm test -- --list
npm test -- test/pi-agent-thread-input.test.js test/pi-agent-threads-limits.test.js
npm test -- --timing
```

- 无文件参数时全量执行；参数为相对仓库根目录的精确 `.test.js` 路径或测试目录，目录递归选择。多个选择取并集、去重并保持统一发现顺序；不支持通配符、任意 Node 参数或仓库外路径。
- `--list` 只列出选中用例文件，不准备 bundle 或执行测试。任何一个选择没有匹配、未知选项或整个发现集合为空都会失败，避免拼写错误变成零测试通过。
- `--timing` 保留 Node TAP 输出、失败和退出码，并追加最慢的至多 10 个文件及 10 个用例/套件。使用 Node 事件中的耗时；旧 Node 没有逐文件 summary 时仅列用例。嵌套耗时重叠，不可相加；文件耗时不含父运行器开销，用例外的准备也不一定进入用例耗时。
- 开发中先跑相关文件；交付按上面的矩阵。不要为了定向运行而绕过环境过滤，也不要在尚未证明用例隔离前提高全量并发。

全量与定向 Node／浏览器入口还移除继承的 `PI_PACKAGE_DIR` 和 `PI_SUBAGENT_`／`PI_SUBAGENTS_` 元数据，使目标 SDK 从本地安装读取版本、独立父 fixture 不误加载 child registration。用例在运行器启动后可明确建立自身 child 配置；原供应商凭据过滤保持。

Node 用例的清理必须先等待网关、worker 和 SQLite 连接关闭，再删除临时目录；Windows 不允许删除仍被打开的数据库。创建恶意符号链接 fixture 的全量测试需要 Windows 的符号链接权限（开发者模式或提升权限的独立测试任务）；应用安装和日常运行不因此要求管理员权限。浏览器与普通权限核心运行另行验证。

## 浏览器与重型专项

按场景定位真实后端 E2E、模拟接口的 UI 回归及准确包／实机脚本，见 [E2E 导航](E2E.md)。

`npm test` **不执行** `test/browser/*.cjs` 或 `test/release/*.cjs`；语法检查和打包发现这些文件不代表执行过它们。

```bash
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser -- --list
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser -- test/browser/pi-workbench.cjs
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser -- --target=desktop test/browser/pi-office-file-preview.cjs
PLAYWRIGHT_MODULE=/path/to/playwright npm run test:browser
```

- 运行器串行执行会启动 Chromium 的脚本，沿用 `npm test` 的凭据过滤；脚本读取的 `*_URL` 统一指向一个只提供 `public/` 与 vendor 静态资源的 loopback 服务，API/WS 仍由脚本自己 mock。单个脚本超时 5 分钟，失败时输出末尾日志并以非零退出。`CHROMIUM_PATH` 可指定浏览器。
- `--target=all|desktop` 默认 `all`，保留各脚本原有桌面和手机场景。用户明确选择仅验桌面时用 `--target=desktop`，共享选择器在运行场景前过滤；运行期 guard 同时检查真实 context／page 创建和 resize，拒绝移动标志或宽度不大于 900 的视口，并拒绝零 context 的假通过，输出实际宽度审计。记录 target，桌面结果不能声称手机已验。这个显式选择不取消仓库其他任务的通用手机回归要求。
- `pivane-browser: office-native` 只标记依赖原生 Office 转换的场景，运行器用 [inventory 的平台声明](../../server/office-preview/inventory.js)判断适用性；未支持平台输出 SKIP 及原因，不计为 PASS，显式选择也不绕过。纯 Excel OPC 场景不需要该标记。`pivane-browser: helper` 为被预加载或复用的辅助代码，不作为可选择场景。
- 每轮运行打印独立截图目录，传给脚本的 `PIVANE_TEST_SCREENSHOT_DIR` 按本轮和脚本隔离。仅按该变量保存的截图可据此关联本轮；仍写固定临时路径的旧脚本须另行保全，不能只凭修改时间认定来源。
- 助手分类管理、辅助模型、记忆聊天外壳、原生完成状态和会话标题的合成脚本屏蔽 Google Fonts 的两个域名，使用系统后备字体，避免外部下载影响页面与截图等待。这些检查不覆盖在线字体可用性；其他网络和业务断言保持原范围。
- 侧栏布局按中文与英文拆为两个自动入口，共用同一套十四场景矩阵与断言。默认发现会运行两项；`PI_SIDE_LAYOUT_WIDTH` 仍可缩小诊断范围，单宽结果不代替完整矩阵。
- 开发和局部本机部署跑受影响脚本及必要集成；共享 UI、累计集成批次和公开发布跑全量，具体按 [验证矩阵](#验证矩阵)。`--list` 可核对精确脚本清单；运行器不会自动推导影响范围或判断结果能否复用。
- 先用一个相关脚本核对 vendor 挂载、浏览器版本与非秘密环境（尤其 `LANG`/`LC_ALL`、时区、下载名），再批跑。环境修正后按影响补验，不复制整个生产环境，也不把环境差异导致的失败直接忽略。
- 首行带 `pivane-browser: manual` 的脚本需要真实隔离服务或发行归档，运行器不执行：按脚本说明显式传入目标 URL，服务分开 Agent、媒体、项目、预约队列等路径且不继承真实供应商认证。**不得指向维护中的实例或依赖默认端口。** 发行安装、升级与恢复按 [发行流程](RELEASING.md) 使用准确归档；Pi 受管联网更新需显式 opt-in 的专用隔离环境。
- 界面有意改变导致脚本失败时，修正期望并保留其独有场景；不要靠放宽超时或删断言让失败消失。UI 专项继续检查桌面/手机、pageerror、实际宽度、抽屉、附件和工具状态。

## 源码发现与发布

`scripts/source-files.cjs` 统一枚举 server、public、scripts 和各类测试，递归发现功能子目录；排除用户媒体、旧工作台、vendor 自动发现、隐藏目录和备份，并拒绝代码符号链接。字体和第三方资源使用明确清单。内置能力的官方发布内容由 `vendor/manifest.json` 单独登记并逐文件校验，通过同一 `distributionFiles()` 纳入发行和受管快照；上游 Markdown 不作为白泽灵台自有指南进行链接改写。

- `check-syntax.cjs` 使用相同发现规则检查应用、测试及受管 TypeScript 扩展的语法，不声称执行 TypeScript 类型检查。
- `run-tests.cjs` 从统一发现的 `.test.js` 集合选择并串行执行，避免依赖平台 shell 展开；可选的 `test-timing-reporter.cjs` 只报告 Node 事件，不改变执行顺序或失败语义。`run-browser-tests.cjs` 使用同一发现规则选择浏览器脚本。
- `package-trial.cjs` 和受管 Pi 更新的源码快照使用相同的 `distributionFiles()`，保留各自的字节、描述符、预算和哈希检查。
- 新增独立资产或文件类型时更新明确清单；新增文档更新 `docs/public-files.json`。改变源码目录还要核对 require/import、HTML 脚本入口、静态访问清单和浏览器 fixture。
- Office 引擎及生成 Worker／模型／声明由 [Office inventory](../../server/office-preview/inventory.js)提供统一资源清单，安装与受管更新、静态访问及发行复用；公开 fixture 的来源／许可证和哈希按[材料说明](../../test/fixtures/office/README.md)维护。预览解析和转换预算以配置为准，文档不另复制常量。

## 文档责任

| 内容 | 主要维护位置 |
|---|---|
| 用户如何操作、限制和排障 | `docs/` 对应功能指南 |
| REST/WebSocket 字段、错误和并发语义 | API 与对应功能契约 |
| 模块职责、依赖方向和设计理由 | `docs/development/` |
| Agent 每次开发要遵守的核心要求 | 根目录 AGENTS.md，详细说明通过链接引用 |
| 当前机器、运行/源码基线、有效授权 | 私有维护仓库或已忽略的本地资料 |
| 历史验收和交接 | 私有归档；公开仅保留版本相关的去敏摘要 |

删除重复或错误的现行说明；有追溯价值的旧资料移入历史索引并标明适用版本。不要把发布说明中的历史限制改成当前状态，也不要把已失效的临时规则反复加载到 Agent 上下文。

## 约定的修改

规则应说明保护的对象和适用条件。会话事实、文件身份、隐私和执行归属属于正确性边界；验证范围、目录布局和维护流程可以根据证据调整。阶段性规则在条件消失后移出当前入口。调整规则需要同时检查实现、文档和自动化，不能通过删除规则掩盖尚未解决的问题。

对于多 Agent 工作，默认一个工作区同一文件只有一个写入者；需要并行写入时使用独立 Git worktree，并在明确的合入点核对结果。只有用户授权委派时才启动其他 Agent。
