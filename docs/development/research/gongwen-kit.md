# gongwen-kit 接入评估

初次核查日期：2026-10-14。上游为 [imhuhe/gongwen-kit](https://github.com/imhuhe/gongwen-kit/tree/d8dfe6a24e20ecaa64c14f3a79159813ad92db70)，源码证据固定提交 `d8dfe6a24e20ecaa64c14f3a79159813ad92db70`。本项目对照基线为 `9111641222ddc4621728420ada4bac447d243b3a`（源码 package.json 版本 1.7.2）。前半部分保留初次源码评估与接入建议；后续讨论及实现状态见文末。2026-10-15 已完成首期源码接入与隔离验证，没有切换运行实例或发布版本；未核对实际运行版。

## 判断与优先级

值得作为可选公文能力接入。最大增量是确定性的数字与格式检查、保留审阅选择权的修订输出；本项目已有附件、原生技能、交付快照和成果库，可复用完整的输入与交付链路。

| 优先级 | 值得引入的能力 | 对白泽灵台的价值 |
|---|---|---|
| 第一 | 数字自洽与体例机检 | 检查分项与合计、跨表取值、正文列举数量、日期与发文字号，给生成结果增加可重复检查 |
| 第一 | 结构化公文生成 | 固定通知、请示、报告、函、纪要、管理办法等构件与版式，减少模型临时拼接 Word 格式 |
| 第二 | 原件保留、修订与批注 | 用户上传旧稿后，另存修订件，规范文字由用户审阅，数字问题交人工核对 |
| 可独立借鉴 | 错误／提示分层、词表和正反标本 | 为报告、方案等中文交付建立质量规则；普通报告需选择适用规则，不能强套公文格式 |

能力范围依据上游 [SKILL.md](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/SKILL.md) 与 [生成核心](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/lib/gongwen-core.js)。以上优先级是结合本项目结构的建议，不是已实现功能。

## 源码确认的亮点与限制

### 数字核对与出稿检查

[check-num.js](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/checks/check-num.js) 检查合计行／列、百分比构成、跨表同指标取值和正文计数与列举。正文同指标多处取值、正文与表格对照属于提示。无声明表头的手写表合计问题降为提示；跨表检查要求声明表头且表头一致；含中文单位、范围或括号负数的单元格可能跳过。因此检查通过只能说明已覆盖规则未发现错误。

同文件使用相对容差 0.5%、绝对下限 0.02，百分比构成容差 0.5 个百分点；跨表对照有自己的数值签名逻辑。金额、预算等严谨场景须另行评估规则和容差，不能把这套检查描述为财务准确性证明。

[writeDoc](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/lib/gongwen-core.js) 在写盘及 XML 补丁之后检查 XML，再依次执行体例、数字、文风三道检查。严格模式失败返回失败状态并设置非零退出码，但文件已写盘；适配层必须检查结果才能标为合格，文件存在不能代表出稿成功。待核对稿可以显式交付，但应标明问题。

### 可审阅的修复输出

[修复入口](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/tools/fix-doc.js) 和 [修复说明](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/docs/修复.md) 将操作分为直接修改版式、规范文字写入 Word 修订、数字问题插入批注三类。原件保留，数字不自动修改。这很适合“上传旧稿 → 核查 → 交付修订稿与报告”的工作流。

“拒绝本工具修订后文字等于原稿”不等于完整恢复原版式。标题识别依赖位置和对齐，主题色红头可能识别失败；默认修复会统一通用公文版式，信函和纪要等特殊原稿应考虑 `--no-layout`。建议首期先提供检查；修复默认保留版式，统一重排作为明确选择。网页只交付修订件，审阅仍在 Word/WPS 等客户端完成，本项目当前没有 Office 在线编辑能力。

发现一处文档与源码边界需实测确认：说明称表格里的数字一个都不改，但 `textPass` 扫描所有 `w:p` 时没有排除表格段落，传给 [文字规则](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/lib/fix/text-rules.js) 的上下文也没有表格标记；全角数字转半角等规则因而可能在表格内产生修订。这是静态源码推断，不表示已经运行复现；它也不同于自动决定应修改哪个合计值。接入前须补表格原字节／文字边界标本，不能照搬该承诺。修复路径未调用生成器的 `checkXmlParts`，输出应另加 XML 完整性验收。

### 规则分层与测试标本

[文风扫描器](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/checks/style-scan.js)、[词表](https://github.com/imhuhe/gongwen-kit/tree/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/data) 和 [测试](https://github.com/imhuhe/gongwen-kit/tree/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/tests) 的可借鉴点是：规范错误与风格提示分开；错误标本验证规则确实报错，正确标本防止误报；修复测试检查接受／拒绝修订后的文字。风格词表可用于中文报告，但套话、术语命中只能提示，引用内容保留，单位词表需另行校准。

## 本项目接入路径

### 先提供可选技能与生成交付

沿用 [内置能力包](../../BUNDLED_CAPABILITIES.md) 的原版源码固定提交、vendor manifest 与逐文件哈希方式，用独立资源登记包暴露上游技能，宿主行为放在本项目适配层。可参考 [演示文稿资源登记](../../../pi-packages/presentations/package.json)、[能力清单](../../../server/pi-bundled-capabilities.js) 和 [资源视图](../../../server/pi-bundled-resources.js)，保留用户启停与受信项目规则。

技能负责选择模板、起草和解释检查结果，原生工具负责执行，最终用 [deliver_files](../../../server/pi-deliverables-extension.ts) 交付 DOCX 与文本／Markdown 检查报告。用户需要长期保留时进入 [成果中心](../../ARTIFACTS.md)。无需新增会话副本或绕过 Supervisor 启动同会话 worker。

上游 [package.json](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/package.json) 声明版本 0.3.1、`private: true`、Node >=18、MIT，以及 docx/jszip/sax 三项运行依赖；它适合固定源码接入，不能假设已有 npm 发布包。本项目根依赖当前没有这三项直接依赖，正式接入须通过现有安装入口统一锁定、核查真实依赖解析，并保留上游许可证。`require_docx()` 专门保证生成器与构件使用同一 docx 实例，接入不要另行混用生成库实例。

### 再接附件检查与修复

现有 [附件服务](../../../server/pi-document-uploads.js) 已能在当前原生分支证明之后提供验证过的 DOCX 原字节；[read_document](../../../server/pi-document-extension.ts) 只返回内容／结构，不保留检查所需的 OOXML 版式。新能力应消费经证明的原字节，不能把提取文字重新拼成 DOCX 冒充原件。

可复用 [独立解析池](../../../server/pi-document-pool.js) 的处理模式：无模型凭据、独立 Node 进程、输入／展开／XML／输出／内存／时间／并发预算，取消后等待真实进程退出，纳入维护等待。本项目当前池仅处理读取，新增检测与修复仍需单独适配和验证，不是直接调用既有工具即可完成。

上游生成器内部使用同步子进程调用检测脚本；修复和检测直接读取路径、加载 ZIP，并非本项目已有的完整描述符与预算边界。应在受管子进程内执行，用验证字节创建受控输入副本，为输出分配独占新路径、拒绝覆盖，并在交付前重新核验输出。不要直接挂进 Express 主进程或对浏览器开放任意文件路径。

建议宿主工具先覆盖“检查附件”和“生成公文”，再增加“另存修订件”。工具名称和参数仍需设计；不要提前写进用户指南或宣称已经支持。

### 报告适配

上游 CLI 输出面向人的文本，没有统一 JSON 协议。[体例检查](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/checks/check-doc.js) 导出 `readDocx/check`，数字检查导出 `check`，文风可调用 `style-scan.scan`；可在宿主包装层显式返回规则、严重程度、定位、覆盖范围、错误／提示与工具故障，保留引文豁免等上游规则。

`check-style.js` 与 `fix-doc.js` 没有受 `require.main` 保护的库入口，直接 require 会执行命令行流程。适配应调用可导出的扫描／检查函数，修复先保留独立进程入口；主项目封装不能假设三类 CLI 都是可导入库。

数字检查返回数组，并把 `hints` 放在数组附加属性上；直接 JSON 序列化该数组会丢失提示，必须显式拆成独立字段。文风现有扫描结果偏文本，转换为统一规则 ID／定位仍有工作量。修复 CLI 也不能仅凭退出码 0 宣称所有检查通过，修复报告可能仍包含待核对问题。

## 正式接入前的验证范围

- 固定提交的干净安装、三项依赖解析和可选技能发现／启停／重载；保留上游测试标本并按本项目统一入口补接入验证。
- 标准模板正常出稿、检查失败与工具故障区分、数字提示完整返回，失败稿不得标为合格。
- 合计、部分占比、不同年度／单位／口径、手写表、引文、已有修订等典型正确与错误标本。
- 原件不变、独占输出、拒绝工具文字修订后的文字一致、旧修订保留；直接版式变化单独核对。
- 上传、当前分支授权、预算、取消后真实退出、停机等待、交付引用与成果保存；若增加 UI，按开发流程使用合成服务做桌面／手机回归。
- 实际目标 Windows Word/WPS 渲染和字体检查。上游 [README](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/README.md) 说明版式主要在 Mac Word 验收，Windows Word/WPS 未逐项渲染验证；跨平台 Node CI 不能代替版式验收。字体另按上游 [字体说明](https://github.com/imhuhe/gongwen-kit/blob/d8dfe6a24e20ecaa64c14f3a79159813ad92db70/docs/字体.md) 准备。PDF 需要另行导出，上游可选 PDF 检查器不能视作转换引擎。

上游的排版和规则检查在本机完成；AI 起草的数据流仍取决于所用模型。该工具不检查材料真实性与政治表述，也不提供审批、签章、OFD 或公文交换系统。正式集成与发布分别按 [开发流程](../WORKFLOW.md) 验收。

## 设计讨论记录

本节记录用户选择与待定事项；实际实现和验收边界单独记录在下节。

- 已确认首期主场景：用户在聊天里描述需求，生成新公文，交付 DOCX 和自动检查报告。
- 已确认接入方式：随应用交付、可启停、统一更新的内置能力，固定上游版本并统一管理运行依赖。
- 已确认文种范围：覆盖上游已有通知、报告、请示、函、纪要、管理办法及非红头企业文书，逐类验证；自定义单位模板留待后续。
- 已确认使用入口：自然语言与现有技能入口，不增加专门的公文生成表单页面。
- 已确认缺失事实处理：影响正文的关键事实先集中追问一次；文号、落款等可留明确占位。用户要求直接出稿时交付待补充草稿，不编造日期、金额、人数或单位信息。
- 已确认检查失败处理：明确的格式、编号和文字规范问题自动修正，最多两轮；数值事实不猜改。仍有错误、占位或未决问题时交付待核对草稿及问题报告，风格提示可保留。自动修正限已生成的新稿，不扩展为旧稿修复。
- 已确认交付范围：DOCX 与 Markdown 检查报告，聊天显示简短摘要；PDF 后续独立评估。
- 已确认草稿术语见 [词汇表](../../../GLOSSARY.md)。
- 已确认启用规则：默认可用，可在现有技能设置中关闭；仅在用户提出相关任务时生成文件。
- 已确认默认版头：非红头；用户明确要求红头时根据提供要素生成，缺失信息按草稿规则处理。
- 已确认字体与版式边界：DOCX 设置规范字体，报告列出所需字体，应用不捆绑字体；规则机检与实际渲染核验分别报告，未渲染时如实标明。
- 已确认单位信息复用：首期使用当前会话与用户选定的现有提示词模板，不新增专门公文配置；跨会话默认单位由用户明确设置，不从单次出稿推定。
- 已确认后续改稿：生成新版本并重新检查，旧版本保留；仅按明确要求修改，日期歧义或数字口径先核对，文档与检查报告对应同一版本。
- 已确认首期验收：各文种样张、正确／错误标本、两轮自动修正、草稿状态与实际下载链路；Windows Word 与 WPS 代表性样张实机渲染，无法完成的检查明确保留未验收项，不用脚本通过替代。
- 已确认数字容差：金额和整数数量按显示精度严格核对；占比仅允许显示位数对应的舍入误差，口径不明列为待核对，不自动改数。
- 已确认检查故障交付：结构有效的已有文件以“检查未完成”草稿交付，并列出故障；没有经过结构验证的文件只交付失败说明，不标为通过。
- 已确认执行范围：继续源码实现与隔离验收；本机部署与公开发布另行安排，未完成实机检查如实列出。
- 2026-10-15 源码接入采用独立 `pivane-gongwen` 登记包与生成工具，上游原始目录保留，结构化输入／数字容差／版本输出等宿主策略位于 `server/gongwen/`，没有直接开放上游生成或修复 CLI。用户操作以[公文生成指南](../../GONGWEN.md)为准。
- 上传旧稿检查和修复不作为首期主场景，是否随后纳入尚未决定。上文早期接入建议按本节已确认范围和实际源码收敛。

## 首期实现与验收边界

源码包含七类新稿生成、独立进程检查、最多两轮规范修正、严格表格数字核对、原生分支交付和版本留存。根目录统一锁定 docx 9.7.1、jszip 3.10.2、sax 1.6.1；上游源码按固定提交逐文件核验。长报告保留总数与节选，原始／最终草稿和完整修正记录分别保存。

隔离验证覆盖上游正反标本、七文种及附件、占位草稿、数字冲突、检查故障、取消／超时、私有文件权限、请求复用、版本保留与实际授权下载；现有相关桌面和手机 Chromium 检查通过。WPS 实机导出七类样张共十八页，逐页检查未见裁切或重叠。标题使用声明的宋体备选，缺少实际小标宋字体，因此未完成规范字体验收；Microsoft Word 未安装，Word 实机验收仍未完成。每份实际交付文件继续如实标注渲染未验证，样张验收不替代用户文件验收。

本次仅为源码与独立候选验证，没有部署或公开发布。完整 Node 回归尚有原有会话目录别名用例的 EEXIST 失败，已在上述基线复现；不将此结果记录为全量通过。精确候选、日志与逐文件哈希按开发流程留在忽略的本机验证资料中。

## 已有稿修订扩展

后续用户确认补齐已有 DOCX 检查、另存修订件、Word 修订痕迹与批注，新稿仍使用结构化输入。源码新增 `revise_gongwen`，从当前分支附件 ID 读取授权原件；只检查保留原字节，规范修订使用上游可导入构件，原件与已有修订／批注保留。通用版式可直接调整，函、纪要及特殊模板可保留版式；主题色自动保留并提示。文字修改待 Word/WPS 审阅，数值问题只批注。此扩展的精确源码、候选和验证证据单独留存，不沿用首期生成样张冒充修订验收；尚未部署或发布。
