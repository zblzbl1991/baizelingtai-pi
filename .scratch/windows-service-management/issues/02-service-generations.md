## Question

怎样在一次托盘生命周期内支持“启动、停止、再次启动”，同时保留安装锁、唯一服务所有者、旧 worker 实际退出和迟到消息的代次校验？决策应给出状态机、所有权边界及故障恢复规则。

## Context

当前 [托盘](../../../scripts/desktop-tray.ps1) 创建一次 Node runner，子进程退出后结束托盘消息循环；[desktop runner](../../../scripts/start-desktop.cjs) 一次调用启动入口；[桌面编排](../../../server/pivane-desktop-launcher.js) 的停机最终进入进程退出。[ManagedLauncher](../../../server/pi-managed-launcher.js) 持有安装锁，关闭后不能直接重用同一对象。产品要求则是停止服务后保留托盘和管理窗口。

## Decision to compare

比较“托盘保留并按次创建短生命周期 runner”和“长期桌面控制进程管理多次 ManagedLauncher 生命周期”。用职责、锁持有区间、旧消息归属、私有 LF 协议及异常清理成本说明取舍；不要因为需要重复启停就新建会话管理器。

## Completion criteria

- 明确托盘、runner、ManagedLauncher、HTTP 服务和 worker 各自所有者，以及运行／停止期间锁由谁持有。
- 给出启动中、运行、检查停机、停机中、已停止、启动失败、停机失败与不确定状态的动作表；命令与响应绑定请求身份和服务代次。
- 描述停止过程中重复双击 EXE、旧 ready/exit 消息迟到、控制管道断开及 runner 异常退出的行为；只有旧身份所有者确定退出后才允许再启动。
- 说明启动失败后如何保持可查看的日志、托盘和既有浏览器错误页；保留重复信号只触发一次异步清理。
- 给出验证场景及相关入口，优先复用 [桌面启动用例](../../../test/pivane-desktop-launcher.test.js)、[统一停机用例](../../../test/pi-process-shutdown.test.js) 和 [托盘实机入口](../../../test/browser/pivane-desktop-launcher.cjs)。

## Answer

采用托盘常驻、每次创建短生命周期 runner 的方案。事实依据是现有 runner 一次性调用、ManagedLauncher 的一次性关闭，以及服务退出后的异步清理链；本答案是确认后的设计，不表示这些新行为已经实现。

工作区包含其他未提交改动，且相关更新能力在讨论期间发生变化。实施时核对当时有效的受管版本、配置与运行路径契约；不把任一中间候选版本当作部署基线。

| 方案 | 所有权与复用 | 主要成本 |
|---|---|---|
| 托盘常驻，每次创建短生命周期 runner | 托盘持有桌面 Mutex/Event；每个 runner 创建全新 ManagedLauncher，复用当前安装锁、受管版本选择及进程退出清理 | 托盘需要跨 runner 代次的状态协调；异常退出必须与有完整清理证明的退出区分 |
| 增加长期桌面控制进程 | 长期控制进程协调多次 ManagedLauncher 生命周期，原生窗口只消费控制投影 | 需要将当前 process.exit、信号注册、控制管道丢失及安装锁等进程级行为改成可重复生命周期；同时增加控制进程的故障恢复契约 |

托盘拥有管理入口；runner/ManagedLauncher 拥有本次服务运行。关闭管理窗口只是隐藏，不关闭控制管道。

### 职责与运行锁

- EXE 保持薄入口。托盘继续基于 native realpath 安装身份使用 Mutex/Event，合并重复双击并保持一个管理窗口。
- 托盘为每次显式启动生成新运行代次；本次 runner 的 stdout、stderr、进程退出回调和日志绑定该代次及其实际进程对象。等待页入口的托盘级归属与跨服务重启恢复按 [慢启动与旧等待页的恢复边界](06-startup-recovery.md) 的后续决策执行，状态投影仍绑定当前代次。
- 每个 runner 只创建一次 ManagedLauncher。ManagedLauncher 自身 nonce 及受管服务私有 IPC 继续保留；桌面代次不能替代内部服务代次。既有维护流程可能在同一 runner 内切换受管服务，外层不得把内部重启误判为整轮停止；这不为管理窗口新增维护执行入口。
- 正常停机沿用服务关闭、Supervisor/原生 worker 清理及进程实际退出的链条。停止服务后 runner 退出，托盘保留；退出白泽灵台则在相同链条完成后退出托盘。
- 停止完成后释放 ManagedLauncher 的运行锁，保留托盘 Mutex；下一次启动重新检查后台服务记录并竞争运行锁。被其他启动方式占用时拒绝接管。运行锁释放与所属服务/worker 实际退出必须有明确先后关系，不能先解锁再等待未知清理。
- 每轮重新解析当前有效配置和受管版本，延续实际身份与持久状态的解析规则；当前有效的受管版本与数据路径不能被启动源码默认值覆盖。

### 协议、退出证明与异常恢复

私有 stdout 继续严格 LF 分帧，日志走 stderr。命令/结果绑定桌面运行代次和请求身份；托盘在处理回调前核对当前实际 runner 对象与代次。旧 ready、error、exit 和异步日志读取结果只归属旧运行，不改变当前窗口状态。

正常停止需有该次停机的完成结果、服务与 worker 已结束的有效证明，以及所属 runner 的实际退出；不能单凭端口空闲、runner PID 消失或任意 exit 0 推断整项清理成功。错误退出即使确认已清理，也保留失败结果；异常断链而无法证明清理完成时进入“状态未知”，阻止新启动，保留诊断入口。具体证明载体应复用可验证的私有消息和持有的进程身份，不信任陈旧 PID 文件。

重复停止复用已有 pending 操作；SIGINT/SIGTERM 继续触发一次统一异步清理。控制管道断开可请求正常停机，但断开本身不提供清理成功证明。显示等待时长只用于说明，不作为强杀或重新启动的依据。

### 状态与动作

| 状态 | 双击 EXE／打开工作台 | 停止服务或退出 | 手动启动 |
|---|---|---|---|
| 已停止且前轮清理已核实 | 发起新一轮启动并按浏览器流程打开 | 停止无操作；退出只关闭托盘 | 可用 |
| 启动中 | 打开本轮等待页，合并重复启动 | 允许请求一次本轮有序收尾；启动完成不能覆盖停止状态 | 禁用 |
| 运行 | 打开本实例工作台 | 进入停机检查；详细事务由后续票据定义 | 禁用 |
| 检查停机／等待用户确认 | 保留工作台用于处理任务，不产生新服务 | 复用当前检查；确认时重查；有阻碍则结束本次请求 | 禁用 |
| 停机中 | 只恢复管理窗口显示进度，不排队重新启动；完成后需要用户再次启动 | 只显示同一次操作状态 | 禁用 |
| 启动失败且清理已核实 | 显示保留的失败反馈；重试必须是用户显式启动 | 可退出托盘 | 可用，重新竞争锁 |
| 停机失败但清理已核实 | 管理窗口保留失败与日志 | 不改写失败结果；可退出托盘 | 可用，作为新的显式操作 |
| 仍在等待／退出事实未知 | 显示管理窗口及原因 | 保留当前操作／诊断状态，不重发停机 | 禁用 |

“显式启动”包含产品已确认的已停止状态双击 EXE。发生失败后保留上一轮错误与日志，重试由用户动作触发；在清理尚未核实的状态中，双击 EXE 只能查看状态，不能触发重试。启动页监听不再随本次 runner 的退出或 ready 后定时退役，而是按后续恢复决策跟随托盘生命周期；退出托盘时关闭，长期日志仍保留。

启动期间的停止/退出先预占本轮收尾状态，再进入统一清理；若服务还在创建，必须等待创建路径与本轮清理共同结算。迟到 ready 不得打开工作台或覆盖停机状态。该意图只是停止本轮服务创建，不取消已经提交且结果不确定的业务请求。

### 实施验收要求

以下场景均须在实施后验证，当前未执行新功能测试：连续两次启动/停止、停止后退出、跨代次迟到 ready/exit、不确定退出阻止启动、正常失败保留日志、停止期间重复双击、启动中请求收尾、控制管道断开、重复信号、运行锁冲突及受管版本变化后重新启动。复用桌面、统一停机和原生托盘用例，用独立身份和合成服务验证；不操作真实实例。
