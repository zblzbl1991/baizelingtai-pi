## Question

怎样让低性能电脑上的启动等待页在短暂失联后继续恢复，并清楚区分启动耗时较长、明确失败与旧运行地址失效？是否需要在同一次托盘生命周期内提供跨服务重启的稳定只读启动入口，且保留服务代次、归属与有界清理？

## Context

2026-10-15，用户确认预约决策后报告：电脑性能较差、启动较慢时，第一张浏览器页面显示断开；重新打开后端口变化，用户若不知情就会留在旧窗口。用户进一步明确故障发生在启动等待页，尚未进入工作台。

[启动页脚本](../../../public/desktop-startup.js) 对一次 `/status` 的超时或网络异常直接显示“启动连接已断开”并 return，不再安排下一次只读查询。[等待页服务](../../../server/pivane-desktop-startup.js) 使用临时端口，每个 createDesktopStartup 调用独立创建地址；关闭后旧地址不再可达。

[ManagedLauncher](../../../server/pi-managed-launcher.js) 还存在独立的 45 秒整体启动上限，超时会请求受管服务停机。该上限在源码中已确认，但尚未证明用户本次是否触发；不能把单次 5 秒状态请求超时、45 秒受管启动上限与等待页 ready 后的监听退役期限混为同一个故障。

## Reproduction

复现脚本 [repro-startup-polling.cjs](../assets/repro-startup-polling.cjs) 只使用公开静态源码与合成状态，不启动 Pi worker、不读取真实身份、不操作真实实例。

| 命令 | 本次结果与含义 |
|---|---|
| `node .scratch/windows-service-management/assets/repro-startup-polling.cjs` | exit 1：真实页面脚本第一次查询遇到合成超时后只请求 1 次，显示“启动连接已断开”，没有重试和跳转；断言原窗口应恢复失败 |
| 同一命令追加 `--no-timeout` | exit 0：只去掉该次超时，starting/ready 两次请求后正常跳转 |
| 同一命令追加 `--ports` | exit 0：同一源码根目录创建两次实际隔离等待页，地址不同；第一张关闭后旧 URL 不可达，第二张仍返回 starting |

前两项在 Node VM 中执行实际页面脚本与合成 DOM，定位轮询控制流；第三项使用真实 loopback 等待页 HTTP。它们不代表低性能机器的原生完整启动验收，也不证明 45 秒上限是用户现场的触发原因。

## Answer

用户对 Q31—Q33 回复“按推荐”，确认以下三项恢复语义。本票据解决的是设计；失败复现尚未因本次确认变绿，运行代码未修改。

### 断线与明确失败分开

单次状态请求超时或临时网络失败显示“正在重新连接”，以有界单次请求和退避继续只读查询。没有可信完整状态时不能宣称服务成功、失败或已退出；收到当前代次明确 error 才显示本轮启动失败。未知 HTTP/JSON 保持不可确认状态，提供诊断提示而不跳转到未知地址。

只读重试不创建服务，不重发停机或业务操作；明确失败不自动重启。再次启动仍由用户动作触发。保留最后一次已核实状态及时间，恢复后只接受当前代次的就绪地址。

### 等待入口跟随托盘生命周期

同一次托盘运行期间保持一个稳定的 loopback 只读等待入口；启动、停止、再次启动服务不更换它的地址。托盘拥有入口与当前状态投影，runner 仍按服务运行代次创建和退出。该调整细化了服务代次票据的等待页归属，不增加第二个业务服务所有者。

同一托盘内，旧等待窗口通过该入口看到已停止、明确失败和新一轮 starting/ready，并可在用户显式重新启动后继续进入工作台。页面不负责触发启动。已进入工作台的页面继续使用现有重连机制。

托盘彻底退出时关闭其只读入口。跨新的托盘进程复用地址或自动接续旧页面不在本次保证范围内；旧页面应保持“无法确认当前状态”的清楚说明，并指引用户双击 EXE 或从当前托盘打开入口，而不是自行扫描端口或推断实例归属。

入口仅提供固定静态资源和状态，继续校验 Host/Origin、请求/响应预算和无缓存策略，不提供启动、停机、配置或凭据接口。入口地址与服务运行锁端口、工作台端口分离；端口冲突拒绝接管未知占用者。宿主实现需在现有托盘／原生组件边界内完成，并验证普通用户权限；不引入管理员权限要求。只有本轮可信代次与就绪检查通过才允许跳转。

### 慢启动时间策略

桌面启动整体等待上限改为可配置，默认 180 秒。正常提示时间过去后显示“启动耗时较长”，继续等待同一次启动，不自动重新启动。配置需校验为有限、合理范围的正值，并明确作用于桌面启动；不得意外改变其他启动方式或 worker 启动等待语义。

单次 HTTP 查询超时与整体启动上限分别处理。真正达到整体上限时记录明确失败、启动正常收尾，并等待退出事实；超时不表示取消已完成，也不表示可以立刻创建新身份所有者。稳定只读入口继续可用，展示失败或收尾状态，使旧窗口不会仅因 runner 退出失去全部反馈。

## Completion criteria

- 用户确认同次启动断线恢复、整体慢启动失败的反馈，以及跨服务重启时旧窗口的期望。
- 原窗口从一次状态超时恢复后可进入正确代次工作台；新服务不得由浏览器重试自动创建，明确失败不自动重启。
- 覆盖错误 JSON/HTTP、地址代次变化、服务就绪后短暂失联、等待页退役、启动失败及用户主动关闭托盘；未知状态保持未知，不能误报成功或停止完成。
- 确定是否调整整体启动上限及其配置边界，并独立验证；保留失败清理、最终上限和唯一服务所有者。
- 将实际修复纳入独立身份的 Node/Chromium 桌面与手机回归；如涉及共享启动或原生宿主，按开发流程扩大验证。当前复现仍为红，不能宣称已经修复或实机验收通过。
