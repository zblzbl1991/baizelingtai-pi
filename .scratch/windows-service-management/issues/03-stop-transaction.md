## Question

怎样生成可信、可定位的停机阻碍事项，并让用户保存草稿后的最终停机提交与新任务、预约和配置写入互斥？需要确定服务端投影与控制协议，覆盖状态读取失败、确认过期、忙碌拒绝和结果不确定。

## Context

当前 [网关装配](../../../server/pi-agent-routes.js) 为维护提供跨服务的 idle 判断；[Supervisor](../../../server/pi-agent-supervisor.js) 与 [worker lifecycle](../../../server/pi-worker-lifecycle.js) 拥有 worker 及后台工作事实；[MaintenanceClient](../../../server/pi-maintenance-client.js) 已有 generation、确认票据和锁，但当前动作列表不包含新的桌面停机事务。

[桌面停机](../../../server/pivane-desktop-launcher.js) 当前接收私有 stdin `stop`，直接调用受管关闭；托盘仅弹通用提示。新的“先列阻碍，再确认，提交时重查”需要设计，不能把现有通用确认当作已完成的空闲核对。

## Completion criteria

- 指定一个跨服务状态投影来源，复用职责所有者；服务端检查与窗口展示使用同一事实，不在托盘复制 worker 字段判断。
- 覆盖 Agent、Shell、侧聊、子任务后台保留、预约派发、媒体、配置/认证、导入导出、会话移动以及其他已登记工作；说明未知或读取失败怎样阻止提交。
- 阻碍事项输出有界类型、数量和定位信息，必要时仅显示通用类型；定位不触发模型、不另开 worker、不传递认证凭据，不包含会话正文。
- 明确检查、保存草稿确认、最终提交、锁预占、新任务拒绝与清理之间的时序；状态变化或确认过期要求重新检查。
- 检查发现阻碍时本次操作结束；不自动等待空闲后执行。最终提交的结果不确定时继续查询同一操作，不能重发变更。
- 预约派发闸门在停机提交时生效，保留预约配置；拒绝或取消停机时恢复闸门状态，不遗留维护锁。
- 将桌面控制限制在拥有者的私有通道；明确是否复用维护确认机制或增加同等保护的桌面协议，不能新增公开 HTTP 停机入口。
- 提出真正能发现“检查空闲后新任务进入”“重复提交”“迟到响应”“状态未知仍停机”等回归的隔离行为测试。

## Answer

### 状态来源与协议

在服务端装配一个共享的停机就绪投影，接收各职责所有者的状态；维护空闲判断和桌面阻碍事项都从它读取。worker 部分复用 lifecycle、Supervisor 的启动/删除/移动/临时会话/后台保留状态，其余工作由所属服务提供有界快照。投影只包含可重建展示信息，不另存聊天或任务事实。

每次快照提供确定的 complete/unknown 状态、服务代次与修订、分组类型和数量，以及可安全定位的标题或会话标识；名称缺失时使用类型摘要。任何来源异常或覆盖不完整都不能生成“可以停机”的确认结果。计数区分同一任务的多种阻碍原因，避免将它误称为多个任务。

桌面沿既有私有 stdin/stdout LF 通道及 ManagedLauncher/服务 IPC 请求检查、确认与提交。命令响应绑定 runner 代次、实际服务代次、请求身份及单次停机操作身份；维护已有 generation/nonce 继续有效，不新增 HTTP 停机入口，不把认证凭据交给托盘。需扩展的确认能力由服务端拥有；不能把当前 maintenance action 列表中不存在的 stop 当作现成能力。

### 停机事务

1. 用户点击停止或退出时预占本轮桌面操作，读取完整停机就绪状态。有阻碍则结束本次操作并展示定位入口，不留下待执行停机。
2. 完整空闲时生成绑定动作、runner/服务代次及过期时间的一次性确认票据，展示保存草稿、未提交编辑和同身份外部写入的提醒。等待用户确认期间保持工作台正常使用，不长期持有全局维护锁。
3. 用户确认后通过同一私有通道提交。服务端在 await 前预占提交互斥，校验票据及当前服务代次、失效条件，建立新变更与派发的闸门，再核对全局状态；中间不能有新工作越过闸门。仅完整空闲才消费票据并接受停机。确认期间如果有影响资格的工作变化，即使随后重新空闲，也需要重新检查和确认。
4. 资格校验失败或发现新阻碍时，清除本次未接受操作，释放为它建立的闸门，不发送真实停机请求；保留其他所有者持有的维护状态。用户处理后重新点击，不自动等空闲再执行。
5. 接受后保留操作身份和单次执行状态，继续统一异步停机。后续双击或重复提交只查询本操作，不能重新执行；浏览器断线、超时或 IPC 回调失败保持结果未知，不能推断取消、空闲或停止成功。
6. 接受之前用户取消确认，只释放本次票据和检查状态。已经接受的停机继续收尾；关闭管理窗口仅隐藏界面，不撤销已提交操作。

启动期间停止属于已解决生命周期票据的有序收尾路径：若业务服务尚未就绪，由当前 runner 关闭新工作入口并等待创建/退出结算；不能为完成停机检查而另启 worker，也不能在迟到 ready 后自动打开工作台。

### 覆盖与展示

保持既有保守空闲语义：Agent、Shell、主线程队列、待确认/不确定控制、侧聊连接及票据、临时会话、子任务后台保留、预约派发、媒体与媒体确认、配置/认证、文档解析、导入导出、会话移动、成果/文件目录后台工作、辅助标题及后台学习等，均由其职责所有者投影。空闲但仍打开的侧聊继续阻碍停机，由用户进入工作台关闭或处理；首批不改变侧聊生命周期。

服务管理窗口只显示类型、数量、可定位的名称和处理说明，提供打开工作台的操作；能安全使用已有定位能力时再定位线程。没有相应能力时给出名称/标识帮助用户查找，不编造新的导航 API，也不触发模型、启动 worker 或替用户取消任务。

普通状态刷新采用只读请求；它本身不占用会导致“永不空闲”的业务活动名额。短暂只读 HTTP 应与真实异步工作区分，不能以连接断开结束业务资格占用；最终闸门应覆盖 HTTP、WebSocket 和后台服务的实际变更入口，而不仅阻止新增 HTTP 请求。

### 调度与维护兼容

桌面停止使用可恢复的内存派发闸门，不调用 deferred.pauseAll()，不更改持久预约配置。cron 与延迟消息都需在实际派发前检查此闸门，覆盖在途查询完成后即将入队的竞态。失败、取消或拒绝只撤销本次预占；停机已经接受后闸门保持到退出。

新 stop 确认复用维护机制的代次、票据、互斥与不确定结果原则，但保留不同操作的副作用和授权范围。既有维护客户端仍按原契约执行，新的桌面入口不意外获得更新/备份能力。预约初始化的 skip/latest 与过期消息语义继续由对应兼容票据决策。

### 实施后的必要行为验证

检查空闲后新 prompt/Shell/媒体/配置进入、确认期间变忙再变空闲、票据过期/跨代次、重复提交、私有通道失联、未知状态拒绝、阻碍后不自动停机、侧聊空闲连接、媒体待确认、子任务后台保留、旧请求迟到以及调度闸门建立时已有 dispatch 正在结算。检查拒绝和取消不得遗留全局锁或持久暂停；操作接受后不能因 UI 消失重放。当前仅核对源码并记录方案，未执行新功能测试。
